# OCR文字の検索方式の比較（2026-10-23）

tobi/qmd（BM25とベクトル検索をRRFで混ぜ、LLMで並べ替えるローカル検索）の方式が、ContextCapのOCR文字の検索に効くかを測った。

## 結論

- いまのFTS（trigramの部分一致）に「1件も当たらない句は前半と後半に割って引き直す」処理を足すだけで、1文字誤読した句の検索がhit@5 0%から100%になった。機械学習は使わない。これを `scripts/contextcap-mcp.py` として入れた
- ベクトル検索は、言い換えた問いでhit@5を44%から72%に上げた。ただし事前に決めた導入の基準は満たさず、埋め込みの計算も重いので入れていない
- qmdそのもの（Node、モデル約2GB）は入れない。クエリ拡張は日本語の問いに中国語を出し、並べ替え（rerank）は1件に1分近くかかった

## 方法

| 項目 | 内容 |
|---|---|
| 対象 | 2026-10-21のmacOSのOCR文字。10分ごとの窓にまとめ、窓の中で同じ行は1回だけにした。101文書、約311万字 |
| 評価する窓 | 本文3,000字以上の窓から無作為に25個（seed 7） |
| a 完全一致 | その窓を含めてその日2窓以下にしか出ない行を、そのまま検索語にする |
| b 1文字誤読 | aの1文字を、OCRで起きやすい置換（ロと口、lと1など）で壊す |
| c 言い換え | 窓の話題を別の言葉で言ったキーワード列。Claudeが書いた |
| 正解 | aとbは、その句を部分文字列として含む窓すべて。cは対象の窓と前後1窓 |
| 指標 | hit@5（上位5窓に正解が入った割合）、MRR@10 |
| 埋め込み | Qwen3-Embedding-0.6B（Q8_0）。qmdは日本語向けにこのモデルを勧めている |

導入の基準は測る前に決めた。qmdの最良の構成が、いまのFTSに対してbとcの平均hit@5で15ポイント以上勝ち、aで5ポイント以上負けないこと。

## 結果

| 構成 | a hit@5 | b hit@5 | c hit@5 | c MRR | 1件の時間 p50 / 最大 |
|---|---|---|---|---|---|
| いまのFTS（全語を含むフレーム） | 100% | 0% | 12% | 0.12 | 188ms / 7.9秒 |
| いまのFTS（当たった語の数で並べる） | 100% | 0% | 44% | 0.27 | 188ms / 7.9秒 |
| 上に「句を前半と後半に割って引き直す」を足す | 100% | 100% | 44% | 0.27 | 未計測 |
| `contextcap_search`（今回入れたもの） | 100% | 100% | 44% | 0.27 | 6〜15ms / 2.1〜4.9秒（2回測った幅） |
| qmd BM25 | 92% | 4% | 12% | 0.10 | 1ms / 10ms |
| qmd ベクトルのみ | 80% | 80% | 72% | 0.54 | 70ms / 125ms |
| qmd BM25＋ベクトル（rerankなし） | 100% | 80% | 72% | 0.53 | 76ms / 184ms |
| 割って引き直すFTS＋ベクトル（RRF、測った後に足した構成） | 100% | 100% | 68% | 0.42 | 未計測 |
| qmd BM25＋ベクトル＋rerank | 未計測 | 未計測 | 未計測 | 未計測 | 1件平均56秒以上 |

- cで無作為に5窓を選んだときのhit@5は14%になる。cの25件のうち、FTSが外してベクトルだけが当てたのは9件、その逆は2件だった
- 導入の基準は満たさなかった。最も近いのは「割って引き直すFTS＋ベクトル」で、bとcの平均がFTSより12ポイント上だった。bはFTSを割るだけで100%に戻るので、差がつかなかった
- rerankありの構成は、72分たっても75件が終わらなかったので止めた。75件で72分を超えたので、1件あたり平均56秒以上かかっている
- `contextcap_search` のbは、句を `"..."` で囲んで渡した結果。囲まずに語ごとに分けると88%に下がった

## qmdについて分かったこと

- BM25の索引は、日本語を1文字ずつ空白で区切ってから作る（`store.js` のCJK正規化）。それでも、いまのtrigramの索引より成績は低かった
- クエリ拡張のモデル（qmd専用に学習した1.7B）は、日本語の問いに中国語の言い換えや、同じ英文を繰り返す仮説文を出した。日本語の検索には使えない
- 埋め込みは1.8チャンク/秒だった（1日分で3,470チャンク、31分52秒）。qmdは1つの文を1回ずつモデルに渡していて、複数の文をまとめて計算していない。起動のたびにMetalのシェーダーのコンパイルエラーが出ていたが、原因は調べていない。速い実装（`llama-server` のバッチ、MLX、Core ML）とは比べていない
- 埋め込みはモデルごとに作り直しになる。全期間（78日）を埋め込み直すと、今の速度で30〜50時間と見積もった（実測ではない）

## 入れたもの、入れなかったもの

入れたもの:

- `scripts/contextcap-mcp.py`。読み取り専用のMCPサーバーで、ツールは `contextcap_search`、`contextcap_timeline`、`contextcap_status` の3つ。検索はSKILL.mdのSQLと同じ経路を通り、10分窓ごとに当たった行だけを返す

入れなかったもの:

- ベクトル検索。入れるなら、先に次の2つを満たす
  1. 埋め込みをまとめて計算する実装で速度を測り直し、毎日の撮影分を無理なく処理できると確かめる
  2. 本人が実際に使う問いでcを測り直す
- qmdのクエリ拡張とrerank
- Androidの文字。端末の `RemoteServer` から読む方法のまま変えていない

## この評価の限界

- cの問いはClaudeが書いた。本人が思い出すときの言い方ではない
- 1日分、25窓、75件しか測っていない
- bは1文字の置換だけを試した。2文字以上の誤読や、文字の抜けは試していない
- 検索語と窓の中身は画面の文字なので、このリポジトリには入れていない
