# ContextCap Android

あとで解析するための画面記録を溜めておく常駐スクリーンショットレコーダー、Android 版。
10 秒に 1 回、画面全体を撮影してローカルに溜め続けるだけのアプリ。

macOS 版（`../macos/`）と同じ思想で、スマホ利用文脈のデータを取ることが目的。

- クリック・入力・送信などの操作は一切しない。撮って保存するだけ
- ネットワーク送信なし。**すべてローカル保存**（`INTERNET` permission すら宣言していない）
- 回収は `adb pull`

## 何をするか

| 項目 | 仕様 |
|------|------|
| 撮影間隔 | 10 秒（`CaptureService.INTERVAL_MS`） |
| 撮影対象 | デフォルトディスプレイ全体 |
| 撮影手段 | `AccessibilityService.takeScreenshot()`（API 30+） |
| 保存形式 | JPEG **常に等倍 quality 75**（適応圧縮は 2026-08-18 に廃止） |
| 保存先 | `<外部ストレージのアプリ領域>/ContextCap/YYYY-MM-DD/HHmmss_SSS[.gN].jpg` |
| 容量上限 | **10GB**。再圧縮せず、14 日超と超過分を古い順に削除 |
| OCR | 撮影直後に ML Kit（日本語）。テキストは `<day>/ocr.jsonl` |
| 重複スキップ | なし（解析用途なので間引かず全部残す） |
| 画面 OFF 中 | 撮影停止（スマホは 1 日の大半が画面 OFF のため） |
| UI | Jetpack Compose + Material 3 Expressive。ホームと全画面ビューアの 2 画面。**常駐通知なし** |
| 自己観測 | ContextCap 自身も撮る。止めたければ「アプリ別」から除外指定する |
| 前面アプリ | 切り替わった時だけ `apps.jsonl` に 1 行残す。通知シェード・キーボードは前面扱いしない |
| 情報のない画面 | DRM 保護・AOD は保存せず、区間だけ `blackouts.jsonl` に残す |
| アプリ別 | 枚数・容量の集計、アプリ単位の一括削除、アプリ単位の撮影除外、名前での絞り込み |
| 撮影しないアプリ | 一覧の先頭に別グループで固定。**画像が 0 枚でも消えない**（消すと解除できなくなる） |
| APK | release 16MB（2026-08-20 実測。うち ML Kit の日本語 OCR が 14MB）。R8 必須で dex は 2.6MB |
| lint | debug / release とも 0 件 |

保存先の実パス:

```
/storage/emulated/0/Android/data/app.imichat.contextcap/files/ContextCap
```

命名規約は macOS 版と**完全に同一**なので、回収後の解析スクリプトが両プラットフォームに効く。

## なぜ MediaProjection ではないのか

Android で画面を撮る標準ルートは MediaProjection だが、**この用途では使えない**。

- **Android 15 QPR1 以降、デバイスがロックされると screen projection は自動停止する。**
  全アプリ対象・targetSdk 非依存・opt-out なし
  （<https://developer.android.com/about/versions/15/behavior-changes-all>）
- consent トークンは 1 回限り。`createScreenCaptureIntent()` の Intent を
  `getMediaProjection()` に 2 回渡すと `SecurityException`
  （<https://developer.android.com/media/grow/media-projection>）

つまりロック解除のたびに「通知タップ → システムダイアログ承諾」の 2 タップが要る。
放置して溜め続けるレコーダーとしては破綻する。

`AccessibilityService.takeScreenshot()` はこれを全部回避する。承諾ダイアログなし、
ロックを跨いで生存、単発呼び出しなので常時 VirtualDisplay より電池も軽い。
Play ストアの審査は通らないが、配布は手動 APK なので問題にならない。

**OS 再起動を跨いでも有効なまま**で、起動後に撮影が自動再開することを確認済み
（エミュレータを強制終了 → 再起動して、アクセシビリティ設定が保持され撮影が続いた）。
MediaProjection では consent が消えるので絶対にできない挙動で、
「入れたら放っておく」運用が成立するかどうかはここで決まる。

**副次的な効果として、ForegroundService も常時通知もバッテリー最適化の除外も不要**になる。
AccessibilityService 自体が system_server にバインドされた OS 管理の常駐プロセスだから。
これがこのアプリのアーキテクチャが薄い理由。

## ビルドと導入

```bash
./scripts/install.sh
```

ビルド → `adb install` → 制限付き設定の解除 → 設定アプリを開くところまでやる。
そのあと手で以下を操作する。

1. Downloaded apps → ContextCap
2. 「Use ContextCap」をオン
3. 確認ダイアログの「Allow」をタップ

有効化すると即座に撮影が始まる。

**アクセシビリティの有効化は adb だけでは完結しない。**
`settings put secure enabled_accessibility_services` は Android 16 では反映されない
（`settings get` が `null` のまま）。UI 操作が必要。

### ツールチェーン

| 項目 | 値 |
|------|-----|
| Android Gradle Plugin | 9.3.0 |
| Gradle | 9.7.0（wrapper で固定） |
| Kotlin | **宣言しない**。AGP 9.0 以降は KGP 2.2.10 が内蔵される |
| Compose Compiler | `org.jetbrains.kotlin.plugin.compose` 2.2.10（内蔵 KGP と同じ値にする） |
| Compose | BOM 2026.08.00 + material3 **1.5.0-alpha26** |
| ビルド用 JDK | Android Studio 同梱の JBR 21 |
| compileSdk / minSdk / targetSdk | 37 / **33** / **37** |

**material3 は alpha を明示指定している。** Material 3 Expressive の API
（`MaterialExpressiveTheme` / `LinearWavyProgressIndicator` / `LoadingIndicator`）は
安定版の 1.4.0 では **internal で使えない**。1.5.0-alpha にしか入っていない（2026-08 実測）。
BOM だけ入れると 1.4.0 に解決されるので、バージョンを直接書いて上書きしている。

**compileSdk は 37 が必須。** Compose 1.12 系が要求する。SDK 37 は
`sdkmanager "platforms;android-37.0"` で入る（安定版の一覧には出ず、プレビュー扱いだが
Android 17 はリリース済み）。cmdline-tools が無ければ先に入れること。

**minSdk は 33。** 元は 30 だったが、`registerReceiver` に
`RECEIVER_NOT_EXPORTED` を渡す 3 引数版が API 33 で追加されたため、
それ未満を切って分岐を消した。切らないと自作 broadcast
（`SETTINGS_CHANGED`）が API 30〜32 で他アプリから送れる状態が残り、lint も error を出す。

**AGP 9.0 以降、`org.jetbrains.kotlin.android` を宣言するとビルドが失敗する。**

```
The 'org.jetbrains.kotlin.android' plugin is no longer required for Kotlin support since AGP 9.0.
```

古い記事の「AGP + kotlin.android を両方書く」構成をコピーしないこと。

JDK は `gradle.properties` の `org.gradle.java.home` で JBR 21 に固定している
（Homebrew の Java 26 では AGP が動かない）。
SDK の場所は `local.properties` の `sdk.dir`。マシン固有なので git 管理しない。

**release では R8 を必ず通す。** Compose は未使用コードが大量に入るため、
`isMinifyEnabled = false` のままだと APK が **23MB** になった（Compose 導入時の実測。今日は測り直していない）。
R8 + リソース shrink 有効での現在値は **1.8MB**（2026-08-16 実測。ほぼ全部が `classes.dex` の 1.6MB で、
アイコンを含むリソースは 100KB 未満）。

release も debug 鍵で署名している。個人用の道具なので、R8 を通した APK を
そのまま実機で確認・運用できる方が都合がいい。

## データの回収

```bash
adb pull /storage/emulated/0/Android/data/app.imichat.contextcap/files/ContextCap ./snapshot
```

`getExternalFilesDir` 配下だが、エミュレータ（Android 16 / API 36）では `adb pull` が通ることを
確認済み。実機で `Permission denied` になる場合は `MANAGE_EXTERNAL_STORAGE` を取って
`/sdcard/ContextCap/` に書く方式へ切り替える（`CaptureService.captureRoot()` を差し替える）。

なお `adb shell run-as` からこのディレクトリには**書き込めない**（`Permission denied`）。
これは run-as シェル側の制約で、アプリ自身の書き込みとは別。
動作確認は run-as ではなくアプリに書かせて行う。

## 容量管理（14 日保持・再圧縮なし）

**再圧縮はしない。** 常に等倍で撮り、撮った瞬間に OCR し、テキストを確定させてから画像を捨てる。
テキストが本体で、画像は一時キャッシュという位置づけ。

- 14 日を過ぎた画像を削除する（`Retention.DEFAULT_RETENTION_DAYS`）
- 14 日以内でも 10GB を超えたら、古い順に追加で削除する
- **OCR が済んでいない画像は絶対に消さない。** 消したらテキストごと永久に失われる
- チェックは 5 分ごと + サービス接続時（削除は日単位の判断なので撮影ごとにやる必要がない）
- 撮影時刻はファイル属性ではなく**パスから解釈する**

容量の見積り（2026-08-18 実測・1080x2400 の端末）: 1 枚 **95.3KB**。10GB に約 10.5 万枚入る。
理論最大 8,640 枚/日 でも 823MB/日 なので 12 日分、観測レート（802 枚/日）なら 130 日分。
macOS 版（1 枚 813KB / 4 日保持）とは桁が違うので、保持日数も別の値にしてある。

### なぜ段階再圧縮をやめたか（2026-08-18）

macOS 版の同一画像の統制実験（60 枚・行数分位で層化・単スレッド計測）で、再圧縮に
**実害しか無い**と分かったため。

| 段 | 平均行数 | 文字保持 | 行近似一致(>=0.85) | 平均 OCR ms |
|----|---------|---------|------------------|-----------|
| gen0（等倍） | 101.0 | 1.000 | 1.000 | 592 |
| g1 (1920/q60) | 97.3 | 0.948 | 0.751 | 575 |
| g2 (1280/q50) | 88.5 | 0.891 | 0.568 | 547 |
| g3 (800/q40) | 24.1 | 0.258 | 0.056 | 327 |

**縮小しても OCR は速くならない。** 時間は解像度ではなく行数に比例する（≒ 5.5ms/行 + 60ms）。
g3 だけ速いのは行数が 1/4 に落ちている＝読めていないから。

macOS 版では順序を間違えた結果、corpus の 39%（20,007 枚）が圧縮後の画像で OCR された。
**Android 版は 10GB に対してまだ 153MB しか溜まっておらず圧縮が一度も走っていなかったので、
同じ損失が起きる前に順序を固定できた。**

`.gN` 接尾辞の**パースは残す**（`CaptureFile.LEGACY_GENERATION_SUFFIXES`）。
既に付いたファイルが残っている環境で、読めないと撮影時刻の解釈と OCR の同一性判定が壊れる。

## OCR（撮影直後）

`OcrIndexer` が ML Kit Text Recognition v2（日本語・bundled）で OCR し、
日付ディレクトリの `ocr.jsonl` に 1 行ずつ追記する（`apps.jsonl` / `blackouts.jsonl` と同じ規約）。

```json
{"t":"HHmmss_SSS","gen":0,"w":1080,"h":2400,"bytes":95000,"lines":25,"ms":154,"status":"ok","text":"..."}
```

- **撮影 tick を待たせない。** 撮影は「保存して enqueue」で終わり
- **キューは 2 段。** 撮影直後の分（fresh）を必ず先に処理し、サービス接続時に拾った未 OCR
  （backlog）は fresh が空の時だけ 1 枚ずつ進める。1 本にすると追いつき処理が終わるまで
  新規撮影が待たされ、「撮った瞬間に OCR」が成立しない
- **並列にしない。** 単一スレッドなので同時に持つ Bitmap は常に 1 枚。1080x2400 の
  ARGB_8888 は約 10MB あり、並列化するとそのまま倍々でメモリを食う
- **Bitmap は必ず `recycle()`。** `hardwareBuffer.close()` を怠って撮影が全部落ちたのと同型の罠
- **縮小しない。** 上記のとおり縮小しても速くならず、テキストだけが壊れる
- `conf` は持たない。macOS 側の実測で「読んだ行の平均確信度」は行数が増えるほど下がる
  非単調な値で、取りこぼし率の代理変数にならないと分かっている
- **`org.json` と `android.util.Log` を `OcrLog` で使わない。** 使うと JVM unit test から
  検証できなくなる（`BlackoutLog` と同じ理由）

### 実測（エミュレータ Android 16 / sdk_gphone64_arm64・2026-08-18）

| | 実測値 |
|---|---|
| OCR スループット | **7.7 枚/秒** |
| 撮影レート | 0.1 枚/秒（10 秒間隔） |
| 余裕 | **77 倍** |
| 1 枚あたり | 平均 129ms / 平均 13 行 |
| 追いつき | 1,701 枚を約 4 分で消化 |
| メモリ | PSS 165MB → 156MB（サステインで減少。リークなし） |
| 撮影 → OCR の遅延 | 最新 jpg と最新 OCR 行が常に一致 |

**実機ではない。** ML Kit の速度・電池は実機で測り直すこと。ただし 77 倍の余裕があるので、
実機が 10 倍遅くても追いつく計算になる。

APK サイズは bundled モデルの分だけ増える。`abiFilters` を `arm64-v8a` に絞って
**release 15.7MB**（絞らないと 44.4MB。うち 39MB が 4 ABI 分の `lib/`）。
x86_64 のエミュレータで動かす必要が出たら `app/build.gradle.kts` に `"x86_64"` を足す（+11MB）。

実機（エミュレータ Android 16）での動作実測:

```
I ContextCap: connected. root=/storage/emulated/0/Android/data/.../ContextCap
I OcrIndexer: 追いつき対象 1701 枚
```

- 1,701 枚の未 OCR を約 4 分（7.7 枚/秒）で消化し、OCR 行数 1,725 = jpg 1,725 枚で一致
- 追いつき中も新規撮影は即 OCR され、最新 jpg と最新 OCR 行が常に一致していた
- PSS は 165MB → 156MB と減少。Bitmap の `recycle()` が効いていてリークしない

なお段階再圧縮を廃止する前は、上限を 12MB に下げると 153 枚 / 14MB → 6.6MB へ押し戻し、
採用段 `adopted=2` が永続化されて新規撮影が `.g2.jpg` になることを確認していた。
**この「撮影プロファイルの劣化」こそが廃止の理由**なので、記録として残しておく。

## 情報のない画面は保存しない

DRM 保護（`FLAG_SECURE`）の画面と AOD は、撮れても中身が真っ黒で情報がない。
2 時間の映画をそのまま撮ると 720 枚の黒い JPEG が積み上がるので、**保存せずに捨てる**。
代わりに区間だけを日付ディレクトリの `blackouts.jsonl` に残す。

```
{"t":"213040_120","state":"start"}
{"t":"231510_880","state":"end"}
```

- 変化点方式は `apps.jsonl` と同じ。状態が変わった瞬間だけ 1 行
- 日付をまたいで黒が続く場合は、翌日のファイルにも `start` を書く（日ごとに読めるようにするため）
- サービスが黒の途中で死ぬと `end` が無いまま残る。解析側は「次のイベントまで」と読む。
  プロセスが落ちて状態が飛ぶと `end` を挟まずに `start` が続くこともあるが、同じ読み方で壊れない
- 黒のまま画面が OFF になった場合、`end` は**画面が戻って最初に撮れた時刻**になる。
  OFF 中も黒区間として続いた扱いになる（撮っていないので実際に観測できていないのは同じ）
- **`apps.jsonl` への記録は黒でも続ける。** 画像が無くても「何を見ていたか」は残す価値がある

### 判定（`FrameBlackness`）

**黒いピクセルの割合では判定できない。** 真っ黒地に白文字のダークモード画面は 9 割以上のピクセルが
黒く、割合だけ見ると保護画面と区別が付かない。違うのは黒の連続性で、保護画面は広い面が丸ごと黒く、
ダークモードは文字が全面に散る。

そこで縮小デコードした画像を 8px 角の格子に割り、「セルの中に輝度 16 を超える点が 1 つも無い」
セルを数える。それが**全体の 85% 以上**なら情報なしと判定する。

85% にしているのは、**保護画面でもステータスバーとナビゲーションバーは通常どおり写る**ため
（Android 16 で実測）。全面が黒くなることは無いので 100% では判定できない。

判定は原寸ではなく長辺 160px まで落としてから行う。`Bitmap.wrapHardwareBuffer` が返す
HARDWARE config の Bitmap は CPU から直接読めないので、**エンコード済みの JPEG を読み直す**。
撮影ごとに原寸を `ARGB_8888` へコピーするより安い。

判定は保存の前に行うので、捨てるフレームはファイルにも `.tmp` にもならない。

### 既に溜まっている黒

遡って消す処理は入れていない。容量が上限に当たれば `Retention` が古い順に消すし、
まず新規の流入を止めるのが先だという判断。

## 画面

**設定画面ではなく観測ダッシュボードとして組んでいる。** 開く目的は設定を変えることではなく
「ちゃんと動いているか」を確かめることなので、主役は撮れている画像と状態に置く。

上から順に:

1. **状態**（記録中 / 一時停止中 / 止まっています）。記録中は
   `LinearWavyProgressIndicator` が次の撮影までの 10 秒を進む。
   放置していても生きていることが目に入るのが、この画面の一番の役目
2. **いま見えているもの** — 最新 1 枚をほぼ全幅で敷く。カードで囲わない
3. **ここまでの流れ** — 直近 20 枚の横スクロール帯。タップで全画面ビューアへ
4. **数字**（枚数・期間・容量・画質・保存先）は最下部に小さく
5. **記録を止める**は目立たせない。誤って止める方が損失が大きい

部品は M3 Expressive の標準を使い、逸脱は構成と言葉でやっている
（設定項目を並べない、画像を主役にする、状態を常時見せる）。

**白ベース。** 地は純白（`#FFFFFF`）のまま沈黙させ、色を持たせるのは
「動いているか」を示す 2 箇所（記録中の緑・止まっている赤）だけにしている。
dynamic color は使わない。端末の壁紙で色が変わると記録中かどうかを色で判断できなくなるため。

**画像は切らない。** ヒーローもサムネイル帯も `ContentScale.Fit` で、
画像そのものの縦横比で表示する。`Crop` にすると上下が欠けて
ステータスバーやアプリのヘッダが見えなくなり、確認の役に立たない。
ヒーローは高さを決めて幅を比率に任せる（幅基準にすると縦長画像で画面を占有してしまう）。

ビューアだけは黒地のまま。画像の色を正しく見るための場所で、
白地だと明るい画像との境界が分からなくなる。

### 自分の画面も撮る

ContextCap を開いている間も撮る。`apps.jsonl` にも `app.imichat.contextcap` として残る。

撮ると直近の記録が ContextCap 自身のスクリーンショットで埋まり、ヒーローもサムネイル帯も
入れ子のフラクタルになる（macOS 版はメニューバー常駐なので起きない問題）。
一度これを嫌って撮影を止める実装にしたが、**記録の連続性が途切れる方が損**という判断で戻した。

嫌なら「アプリ別」から ContextCap 自身を除外指定すれば止まる。
特別扱いをコードに埋め込まず、他のアプリと同じ仕組みで止められる方が筋が通る。

見るための実装で気をつけている点:

- **一覧取得で全件走査をしない。** `CaptureBrowser` は日付ディレクトリ名を降順に辿り、
  必要な件数が揃った時点で打ち切る。`StatsStore` のフルスキャンは 10 万件で 5 秒（ANR 閾値）に
  達するので、閲覧のたびにそれを払うわけにはいかない
- **原寸でデコードしない。** 1080×2364 を `ARGB_8888` で読むと 1 枚 10MB 近い。
  `CaptureThumbnail` が `inJustDecodeBounds` でサイズを見てから `inSampleSize` を決める
- **表示中の Bitmap は 1 枚だけ持ち、差し替えのたびに前を `recycle()` する。**
  20 回連続で切り替えて Java Heap の増加が 164KB（誤差）、OOM 0 件を確認済み
- 探索もデコードも UI スレッドから外している
- **アプリ別の一覧は画像だけを起点にしない。** 集計は保存済みの JPG を走査して行を作るので、
  除外指定したアプリの画像を全部消すと行そのものが生まれず、一覧から消えて**解除できなくなる**
  （設定自体は `SharedPreferences` に残っているのに UI から触れない）。
  `AppUsageStats.collect` は除外セットを受け取り、0 枚でも行を返す。
  逆に**除外を解除した直後も 0 枚の行を消さない**（`HomeState.unexcludedHere`）。
  消すと気が変わっても止め直せず、同じ袋小路に入る

ビューアはスワイプではなく前後ボタンにしている。ページャを足す分の実装と、
横スクロール帯からの遷移との一貫性を考えると、ボタン 2 つで足りる。

## テスト時のパラメータ変更

macOS 版は `defaults write` で差し替えられるが、Android 版は**定数を書き換えて再ビルドする**。
Gradle の差分ビルドは数秒で終わるし、`am broadcast` を受ける debug レシーバーを置くのは
「Service を 1 個も立てない」方針と釣り合わないため。

書き換える定数は `CaptureService` の companion object に集約してある。

| 定数 | 用途 |
|------|------|
| `INTERVAL_MS` | 撮影間隔 |
| `DEFAULT_BUDGET_BYTES` | 容量上限（`Retention` の動作確認時に小さくする） |
| `RETENTION_INTERVAL_MS` | 保持期間・容量チェックの間隔 |
| `FULL_RES_QUALITY` | 保存する JPEG の品質 |
| `captureRoot()` | 保存先 |

## テスト

```bash
./gradlew :app:testDebugUnitTest
```

`CaptureFile` / `StatsStore` / `Retention` / `OcrLog` は Android 依存を持たない純粋ロジックなので
JVM unit test だけで検証できる。`Retention` は現在時刻と容量上限を外から注入する設計にして、
走査・保持判断・**未 OCR ガード**をテスト可能にしている。

`OcrLog` が `org.json` と `android.util.Log` を使わないのはこのため。使うと JVM unit test で
`RuntimeException` / `NullPointerException` になって検証できなくなる（`BlackoutLog` と同じ理由）。

撮影そのものは実機・エミュレータでしか検証できない。

## 実測で確認した範囲（2026-08-13〜14）

すべてエミュレータ（Android 16 / API 36、Medium_Phone AVD）での結果。

| 項目 | 結果 |
|------|------|
| 撮影 | 10 秒間隔。`adb pull` した JPEG に画面が写っている（1080×2400、1 枚 ~125KB） |
| 30 分連続 | 178 枚（期待値 約 180）、エラー 0 |
| メモリ | 起動後 40MB → 46MB で頭打ち。その後 5 分間 TOTAL PSS が 45618KB から動かず（Java Heap は微減）。**リークなし** |
| 画面 OFF / ON | OFF 中の増分 0、ON で再開 |
| OS 再起動 | アクセシビリティが有効なまま残り、撮影が自動再開 |
| 一時停止トグル | 停止中の増分 0、再開後は通常どおり |
| Retention | 未 OCR ガードを含め unit test 7 件 pass。OCR 済みだけ消え、未 OCR は残る |
| OCR | 1,701 枚の追いつきを約 4 分で消化、以降は撮影と 1:1 で追随 |
| `FLAG_SECURE` | **撮影は成功し、該当領域が黒塗りの画像が保存される。**撮影は止まらず、サービスも落ちない |
| unit test | 28 件 pass |

`FLAG_SECURE` の結果は当初の想定と違った。「撮影失敗になるので写らない」と考えていたが、
実際には**ファイルは保存され、中身だけが黒くなる**。プライバシー上の保護は効いているが、
**情報量ゼロの黒画像が容量を食い、解析時のノイズになる**。

中身が無いのに「暗い画面が写っている」ものとして読まれると解析結果が静かに壊れるので、
**収集データを解析に回すときは黒画像を除外する**こと。
現在は全面が黒いフレームを保存前に捨てているが、部分的に黒い画面はそのまま残る。

### 長時間停止からの復帰

検証中に、ホストの macOS がスリープしてエミュレータごと **67 分間止まった**ことがあった
（`pmset -g log` の Sleep 05:02:43 / Wake 06:10:00 と、撮影の空白 05:02:37 → 06:10:03 が一致）。

復帰後 **3 秒で撮影が自動再開**している。端末が長時間スリープして戻る状況と同じなので、
tick が死んだまま放置されないことの実証になる。

撮影間隔は 96 分間の全サンプルのうち **94% が 10.1 秒**。残りはホスト負荷による揺れで、
最大 188 秒の遅延が 1 件あった（実機ではなくエミュレータ由来の可能性が高い）。

**エミュレータで長時間検証をするときは、ホストのスリープを止めないと測定が壊れる**
（`caffeinate -i` など）。撮影の空白を見つけたらまず `pmset -g log` を確認すること。

### 大量ファイル時の UI 応答（実測して直した）

規約どおりのダミーを 8,684 件置いて `SetupActivity` の起動時間を測った。

| ファイル数 | 修正前 | 修正後 |
|---|---|---|
| 47 件 | 22ms | — |
| 8,684 件 | **470ms** | **20ms** |

修正前は 1 ファイルあたり約 0.05ms でファイル数に比例していた。外挿すると
**10 万ファイルで 5.2 秒 = ANR 閾値超え**。10 秒間隔・画面 ON 4 時間/日 なら
2 ヶ月ちょっとで到達するので、「入れたら放っておく」という想定運用そのもので踏む。

`SetupActivity` のフルスキャンを専用 executor へ逃がし、統計欄は「集計中…」を出してから
差し替えるようにした。権限状態とボタンは `SharedPreferences` を読むだけなので UI スレッドのまま。
これでファイル数に依存しなくなった。

`CaptureService` 側の `StatsStore` 生成と `rescan()` は元から worker スレッドなので影響なし。

### 実機（Pixel 10 Pro Fold / Android 17）で確認したこと

| 項目 | 結果 |
|------|------|
| 上書きインストール | `adb install -r` で**撮影データ 6,923 枚がそのまま残る**。アクセシビリティ許可も保持され、`firstInstallTime` は据え置きで `lastUpdateTime` だけ更新される |
| standby bucket | **5 = EXEMPTED**。アクセシビリティサービスなので OS がバッテリー制限から除外している |
| 折りたたみ | 開いた状態では `displayId 0` に **Inner Display が割り当たる**（2076×2152）。実際に撮れた画像も同じ解像度で、`Display.DEFAULT_DISPLAY` のままで内側が撮れる |
| `adb pull` | 通る（`MANAGE_EXTERNAL_STORAGE` 不要） |

**`AccessibilityManager.getEnabledAccessibilityServiceList()` は使わないこと。**
Android 17 の実機では、有効になっていても自分自身が返ってこなかった
（Android 16 のエミュレータでは返る。**同じ APK で挙動が違った**）。
撮影は動いているのに画面が「権限がありません」と誤表示する事故になる。
`Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` を直接読む。

**未検証**（把握したうえで残しているもの）:
- **3 時間以上の無停止稼働**。最長の無停止記録は 30 分（178 枚 / エラー 0 / メモリ平坦）。
  それ以上はホストのスリープに阻まれて測れていない。リークと停止の判定については
  「30 分無停止 + メモリが 5 分間 1KB も動かない + 67 分停止からの自動復帰」で
  足りていると判断して打ち切った
- **数十万ファイル規模での累積挙動**。g3 まで落ちた状態で 10GB を使い切ると
  50 万ファイル前後になり、フルスキャンは worker 上でも 25 秒程度かかる計算。
  統計表示が遅れるだけで撮影は止まらないが、体感が問題になるならキャッシュが要る

## 実装上の注意

- **`ScreenshotResult.hardwareBuffer` は必ず `close()` する。**
  怠るとバッファが枯渇して以降の撮影が全部落ちる（`finally` で閉じている）
- **`FLAG_SECURE` のウィンドウは黒塗りで保存される。撮影自体は成功する。**
  SDK には `ERROR_TAKE_SCREENSHOT_SECURE_WINDOW`（= 6）があるが、
  Android 16 で実測したところ**このエラーは返らず**、該当領域が真っ黒になった画像が
  そのままファイルとして残った（ステータスバーとナビゲーションバーは通常どおり写る）。
  エラー 6 を返す端末があるかもしれないので分岐は残してある。
  検証用の画面は `app/src/debug/.../SecureTestActivity.kt`（debug ビルド専用）
- レート制限は `ACCESSIBILITY_TAKE_SCREENSHOT_REQUEST_INTERVAL_TIMES_MS = 333`(ms)。
  10 秒間隔なら余裕
- 撮影ループは callback 駆動なので、`takeScreenshot` が callback を呼ばずに終わると
  二度と再開しない。`STALL_THRESHOLD_MS`（60 秒）を超えて沈黙したら tick を叩き直す
  watchdog を 5 分ごとの容量チェックに相乗りさせている
- **OCR と削除は撮影用 worker と別スレッドで回す。** 同じ single thread executor に乗せると、
  処理中に撮影の callback が詰まって tick が止まる。ただし OCR 自体は**並列にしない** —
  1080x2400 の ARGB_8888 は約 10MB あり、並列化するとそのままメモリを食う
- `ACTION_SCREEN_ON` / `ACTION_SCREEN_OFF` は manifest 静的登録できない。動的登録が必須
- 3 引数版 `registerReceiver` は API 33 で追加。minSdk を 33 に上げて分岐を消した
- **情報のない画面の判定は保存の前に置く。** 後段（`Retention` や解析側）で落とす設計にすると、
  一度ファイルとして書かれてしまい、除外を忘れた解析が黒画像を読んでしまう
- **`StatsStore` のフルスキャンを UI スレッドで走らせない。**
  ファイル数に比例し、実測で 1 件あたり約 0.05ms（10 万件で 5 秒超 = ANR）
- **`TYPE_WINDOW_STATE_CHANGED` のパッケージ名をそのまま前面アプリにしない。**
  通知シェード・ステータスバー・音量バー・ロック画面・キーボードが開いた瞬間にもイベントが
  飛ぶのに、**閉じた時に元アプリのイベントは飛ばない**（元アプリのウィンドウは変わっていない
  ため）。そのまま記録すると `com.android.systemui` に張り付いて二度と戻らない。
  実機 7 日分 25,400 フレームで測ったら **37%（9,483 枚）が誤帰属**していた
  （区間数 871・合計 64 時間・最長 1 区間 348 分。IME も同じ理由で 781 枚）。
  中身を OCR で読むと実際は YouTube や X の画面。判定は `OverlayPackages`
  （unit test あり）。IME は決め打ちにせず `InputMethodManager` から実行時に取る。
  **ランチャーは除外しない** — ホーム画面は実際に前面にあるため。<br>
  残る限界: オーバーレイを経由してアプリを切り替えた場合（最近のアプリ経由など）は
  イベント自体が飛ばないので、**直前のアプリのまま記録される**。修正後も直らない。
  既に書かれた `apps.jsonl` も遡って直らないので、過去データの解析では
  systemui 区間を直前の実アプリで補間する（`scripts/companion-sim.py` の `pkg_eff`）。

## macOS 版との差分

| 項目 | macOS 版 | Android 版 | 理由 |
|------|---------|-----------|------|
| 撮影間隔 | 5 秒 | 10 秒 | 端末の容量制約 |
| 容量上限 | 40GB / 4 日保持 | 10GB / 14 日保持 | 1 枚が 813KB vs 95.3KB で桁が違う |
| OCR | Apple Vision | ML Kit（日本語・bundled） | どちらも撮影直後・並列なし |
| 段階再圧縮 | 廃止 | 廃止 | 縮小しても OCR は速くならず、テキストだけが壊れる |
| 撮影手段 | ScreenCaptureKit | AccessibilityService | Android に相当 API がない |
| 常駐 | メニューバー | AccessibilityService | 通知を持たない分こちらの方が軽い |
| 画面 OFF 中 | 失敗を無視 | 能動的に停止 | スマホは画面 OFF の時間が長い |
| 黒い画面 | そのまま保存 | 保存せず区間だけ記録 | 未移植。Android 側で効果を見てから |
| 自動起動 | `SMAppService` | 不要 | 有効化した時点で永続 |

macOS 版の README は圧縮段を「最大幅」と書いているが、実装は
`kCGImageSourceThumbnailMaxPixelSize`（長辺）なので、Android 版の「長辺」は
macOS 版の**実装**と一致する。

## プライバシー上の性質

macOS 版と同じ扱いだが、スマホは PC より機微な情報が写る頻度が高い。

- 画面全体を 10 秒おきに撮るため、通知・メッセージ・位置情報・決済画面が写り得る
- `FLAG_SECURE` が立っている画面（多くの銀行・決済アプリ）は、**ファイル自体は保存されるが
  中身が黒く塗られる**（Android 16 で実測）。中身は残らないが、アプリ側の宣言に依存するので
  保護の保証にはならない
- ネットワーク送信機構を持たないので、データは `adb pull` するまで端末内に留まる
- 回収したデータを解析に使う際は、PII を含む前提で扱う
